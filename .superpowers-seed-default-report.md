## Request body shape (for the native client)

```
POST /api/alerts/seed-default
Content-Type: application/json   (optional — omitting the body entirely is still supported)

{
  "beach_id": "<uuid>"   // optional
}
```

- Field name is `beach_id` (snake_case), matching the sibling `POST /api/alerts/rules` body
  convention already in this codebase.
- Omit the field (or send no body at all) → unchanged behavior: seeds on `profile.home_beach_id`,
  rule names read "... at your home break". Verified byte-for-byte via a test that simulates a real
  `NextRequest.json()` rejection on an empty body (what native currently sends).
- Supply `beach_id` equal to the user's home beach → same as omitting it (`isHomeBeach: true`
  internally, "your home break" naming).
- Supply `beach_id` different from home → seeds on that beach; rule names use the beach's actual
  name (e.g. "Mellow session at Waves Point") instead of "your home break".

## Validation error for an unknown/invalid beach id

Standard `createValidationError` shape (matches this route's existing `home_beach_id_required`
convention), HTTP 400:

```json
{
  "success": false,
  "error": "beach_not_found",
  "details": undefined,
  "timestamp": "<ISO>"
}
```

Returned both when `beach_id` is a well-formed UUID with no matching row in `beaches`, and when
it's not a valid UUID at all (format-checked via the existing `isValidUuid` helper before hitting
the database, same pattern as `validateUuidParam`). `seedDefaultRulesForUser` is not called in
either case.

## Implementation notes

- `seedDefaultRulesForUser` gained an optional `isHomeBeach?: boolean` param, defaulting to `true`
  — so the other existing caller (`actions/onboarding-actions.ts`, the web onboarding path, which
  always seeds on the home beach) needed zero changes.
- `nameForPreset` now takes a `location` string instead of hardcoding "your home break"; the route
  passes `"your home break"` when `isHomeBeach` is true and the beach's real name otherwise. The
  five preset name strings are byte-identical to before in the home-beach case.
- Idempotency contract untouched: `already_has_rules` still short-circuits before any beach
  validation or insert.
