# Beach Photos Orphaned Records Cleanup - Migration Summary

**Migration ID:** 20251115163857
**Created:** 2025-11-15
**Type:** Data Cleanup & Integrity Fix
**Status:** Ready for Deployment

## Overview

This migration addresses a critical data integrity issue in the `beach_photos` table where 503 out of 505 photos reference non-existent beaches (74 unique beach IDs that don't exist in the `beaches` table).

## Problem Statement

### Current State
- **Total beach_photos:** 505
- **Orphaned photos:** 503 (~99.6%)
- **Valid photos:** 2 (Avila Beach, Carmel River State Beach)
- **Orphaned beach IDs:** 74 unique non-existent beach references

### Root Cause
Photos were imported into the database without validating that the referenced beaches existed, despite the presence of a foreign key constraint. This suggests:
1. Data was imported with constraints temporarily disabled, OR
2. Constraint validation was deferred/not validated, OR
3. Photos were inserted before beaches were properly seeded

### Impact
- **Data Integrity:** Violated referential integrity
- **Application Performance:** Queries joining beaches and photos may return unexpected results
- **User Experience:** Featured photos view may be empty or show incorrect associations
- **Database Reliability:** Cascading deletes cannot work properly with orphaned records

## Solution

### Migration Files

1. **Main Migration:** `20251115163857_cleanup_orphaned_beach_photos.sql`

### Migration Steps

The migration performs the following operations:

#### Step 1: Backup Orphaned Records
```sql
CREATE TEMP TABLE orphaned_beach_photos_backup AS
SELECT bp.*, NOW() AS deleted_at, 'orphaned_cleanup_20251115' AS deletion_reason
FROM public.beach_photos bp
WHERE NOT EXISTS (SELECT 1 FROM public.beaches b WHERE b.id = bp.beach_id);
```

#### Step 2: Delete Orphaned Records
```sql
DELETE FROM public.beach_photos
WHERE id IN (SELECT id FROM orphaned_beach_photos_backup);
```

#### Step 3: Verify FK Constraint
- Confirms foreign key constraint exists

#### Step 5: Audit Trail

## Database Schema

### Foreign Key Constraint

The existing constraint that should prevent orphaned records:

```sql
ALTER TABLE public.beach_photos
    ADD CONSTRAINT beach_photos_beach_id_fkey
    FOREIGN KEY (beach_id)
    REFERENCES public.beaches(id)
    ON DELETE CASCADE;
```

**Key Points:**
- `ON DELETE CASCADE`: When a beach is deleted, all associated photos are automatically deleted
- This constraint prevents inserting photos with non-existent beach_id values
- The migration verifies this constraint exists and is enforced

### Audit Table Schema

New table created for cleanup audit trail:

```sql
CREATE TABLE IF NOT EXISTS public.data_cleanup_audit (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cleanup_date TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    table_name TEXT NOT NULL,
    records_affected INTEGER NOT NULL,
    cleanup_reason TEXT NOT NULL,
    backup_data JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## Questions & Answers

**Q: Why not just fix the beach_id values instead of deleting?**
A: We don't have mapping data to know which beach each orphaned photo should belong to. The beach IDs don't exist in our database.

**Q: Can we recover the deleted photos?**
A: Yes, all deleted records are backed up in the `data_cleanup_audit` table with full metadata. The rollback migration can restore them.

**Q: Will this affect existing beach pages?**
A: Currently only 2 beaches have photos (Avila Beach, Carmel River State Beach). These are preserved. Other beaches already have no photos.

**Q: What if we import beaches later that match the deleted photo beach_ids?**
A: You can restore the photos from the audit table and remap them to the correct beaches.

**Q: Why did this happen?**
A: Photos were imported before beaches existed, or with FK constraints disabled. Going forward, validation should prevent this.
