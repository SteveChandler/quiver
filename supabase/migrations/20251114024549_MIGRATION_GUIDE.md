# Migration Guide: Automatic Profile Creation Trigger

## Overview

This migration implements automatic profile creation when users sign up. It solves critical issues with user onboarding and E2E test reliability.

### Problem Statement

**Current Issues:**
1. Users created in `auth.users` don't automatically get `profiles` records
2. Application fallback pattern exists but doesn't populate `email` field
3. E2E tests fail when querying `profiles` by email (field is empty)
4. Race conditions in manual profile creation during concurrent signups
5. OAuth signups may lose avatar_url from metadata

**Impact:**
- E2E test suite has flaky failures
- User experience degraded (missing profile data)
- Application code has complex fallback logic
- Data inconsistency between `auth.users` and `profiles`

## Solution Design

### Architecture Decisions

1. **SECURITY DEFINER Function**
   - **Why:** Bypasses RLS INSERT policy that requires `auth.uid() = id`
   - **Safety:** Limited scope, only creates profiles, uses `search_path = public`
   - **Alternative Rejected:** Modifying RLS policy would weaken security

2. **AFTER INSERT Trigger**
   - **Why:** Runs after `auth.users` record is committed
   - **Safety:** User creation succeeds even if profile creation fails
   - **Alternative Rejected:** BEFORE trigger would block signup on failure

3. **ON CONFLICT DO NOTHING**
   - **Why:** Handles duplicate profile creation attempts gracefully
   - **Safety:** Idempotent - safe to retry
   - **Alternative Rejected:** ON CONFLICT UPDATE unnecessary complexity

4. **Exception Handling**
   - **Why:** Logs warnings but doesn't block user signup
   - **Safety:** User experience > data perfection
   - **Monitoring:** Warnings appear in Supabase logs for investigation

### Data Flow

```
User Signup Request
       ↓
auth.users INSERT
       ↓
Trigger Fires: on_auth_user_created
       ↓
Function Executes: handle_new_user()
       ↓
profiles INSERT (with email populated)
       ↓
Signup Success
```

### Edge Cases Handled

| Edge Case | Handling | Result |
|-----------|----------|--------|
| NULL email | Should not happen (auth requires email) | Empty string fallback |
| Missing `full_name` metadata | `COALESCE(..., '')` | Empty string stored |
| Missing `avatar_url` metadata | Direct JSON extraction | NULL stored |
| Duplicate profile attempt | `ON CONFLICT (id) DO NOTHING` | No error, existing profile kept |
| Trigger function fails | `EXCEPTION WHEN OTHERS` | Warning logged, signup succeeds |
| OAuth signup with avatar | `raw_user_meta_data->>'avatar_url'` | Avatar URL extracted and stored |

## Field Mapping

### Source: auth.users → Target: profiles

| profiles Column | Source | Fallback | Notes |
|----------------|---------|----------|-------|
| `id` | `NEW.id` | N/A | Primary key from auth.users |
| `email` | `NEW.email` | N/A | **Critical fix for E2E tests** |
| `full_name` | `raw_user_meta_data->>'full_name'` | `''` | Empty string if not provided |
| `avatar_url` | `raw_user_meta_data->>'avatar_url'` | NULL | Common in OAuth signups |
| `created_at` | `NOW()` | N/A | Timestamp of profile creation |
| `updated_at` | `NOW()` | N/A | Initially same as created_at |

### Fields NOT Populated

All other `profiles` fields use their default values:
- `bio`, `location`, `instagram`: NULL
- `experience_level`, `surf_styles`: NULL
- Notification preferences: Default boolean values from table schema
- Onboarding fields: NULL (populated during onboarding flow)
- Counts: 0 or NULL (managed by application)

**Why:** These fields are populated during onboarding or user profile editing flows.

## Security Considerations

### SECURITY DEFINER Safety

**Risk:** Function runs with elevated privileges (bypass RLS)

**Mitigations:**
1. **`SET search_path = public`** - Prevents search_path injection attacks
2. **Limited Scope** - Only INSERTs into `profiles`, no UPDATEs/DELETEs
3. **Input Validation** - Uses only `NEW` record from trigger (trusted source)
4. **ON CONFLICT** - Prevents privilege escalation via duplicates
5. **Grant Limited** - Only `service_role` has EXECUTE permission

### Why This Approach is Secure

```sql
-- The function:
-- ✅ Only executes in auth.users insert context (can't be called directly by users)
-- ✅ Only creates profiles, never modifies existing ones (ON CONFLICT DO NOTHING)
-- ✅ Uses trusted data from auth system (NEW.id, NEW.email)
-- ✅ Sets search_path to prevent malicious schema injection
-- ✅ Has error handling that doesn't leak sensitive info
```

### Attack Vectors Considered

| Attack | Mitigation |
|--------|-----------|
| SQL Injection | Uses parameterized inserts, no dynamic SQL |
| Privilege Escalation | ON CONFLICT prevents modifying existing profiles |
| Schema Injection | `search_path = public` prevents malicious schemas |
| Resource Exhaustion | Trigger only fires once per user signup |
| Data Tampering | Only creates new records, never updates |

## Rollback Procedure

### When to Rollback

Rollback if:
- Trigger causes signup failures (check error rates)
- Database performance degrades significantly
- Data corruption detected in profiles table
- Unexpected errors in production logs

### Rollback Commands

```sql
-- Step 1: Drop the trigger (stops new profile creation)
DROP TRIGGER IF EXISTS on_auth_user_created ON auth.users;

-- Step 2: Drop the function
DROP FUNCTION IF EXISTS public.handle_new_user();

-- Step 3: Verify removal
SELECT routine_name FROM information_schema.routines
WHERE routine_name = 'handle_new_user';
-- Should return 0 rows

SELECT trigger_name FROM information_schema.triggers
WHERE trigger_name = 'on_auth_user_created';
-- Should return 0 rows
```

### Post-Rollback Actions

1. **Re-enable Manual Profile Creation** (if disabled)
2. **Monitor Signup Success Rate** - Should return to baseline
3. **Investigate Root Cause** - Check logs for trigger failures
4. **Plan Fix** - Address issues before re-attempting migration

## Backfill Considerations

### Do We Need a Backfill?

**Question:** Should we create profiles for existing auth.users records that don't have profiles?

**Analysis:**
```sql
-- Check how many users lack profiles
SELECT COUNT(*) as users_without_profiles
FROM auth.users u
LEFT JOIN profiles p ON u.id = p.id
WHERE p.id IS NULL;
```

**Decision Matrix:**

| Users Without Profiles | Recommendation |
|------------------------|----------------|
| 0 | No backfill needed ✅ |
| 1-10 | Manual backfill (low priority) |
| 10-100 | Scripted backfill (medium priority) |
| 100+ | Backfill migration required (high priority) |

### Backfill Script (If Needed)

```sql
-- CAUTION: Test in development first!
-- This creates profiles for all auth.users without profiles

INSERT INTO public.profiles (
  id,
  email,
  full_name,
  avatar_url,
  created_at,
  updated_at
)
SELECT
  u.id,
  u.email,
  COALESCE(u.raw_user_meta_data->>'full_name', ''),
  u.raw_user_meta_data->>'avatar_url',
  COALESCE(u.created_at, NOW()),
  NOW()
FROM auth.users u
LEFT JOIN profiles p ON u.id = p.id
WHERE p.id IS NULL
ON CONFLICT (id) DO NOTHING;

-- Verify backfill
SELECT COUNT(*) as backfilled_count
FROM profiles
WHERE created_at > NOW() - INTERVAL '5 minutes';
```

## FAQ

### Q: Why not use a Supabase Edge Function?
**A:** Triggers are more reliable (no network dependency), faster (<10ms vs ~100ms), and atomic with the signup transaction. Edge Functions are better for complex workflows that don't need to be atomic.

### Q: What happens if the trigger fails?
**A:** The exception handler catches failures, logs a warning, and allows signup to proceed. This prioritizes user experience over perfect data consistency. The application fallback pattern can still create profiles manually.

### Q: Can users bypass profile creation?
**A:** No. The trigger runs in the database layer automatically. There's no way to create an auth.users record without triggering profile creation (unless the trigger is explicitly dropped).

### Q: How do we handle custom profile fields later?
**A:** The trigger creates the minimal required profile. Custom fields are populated during onboarding or profile editing flows. The trigger doesn't interfere with user-initiated updates.

### Q: What about performance at scale (10k+ signups/day)?
**A:** The trigger adds ~20ms overhead per signup. At 10k signups/day (~7 signups/min), this is negligible. The `profiles` table can handle millions of rows with proper indexing (already in place).

### Q: Can we modify the trigger later?
**A:** Yes. Use `CREATE OR REPLACE FUNCTION` to update the logic. Changes apply immediately to new signups without downtime.
