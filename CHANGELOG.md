### Infrastructure
- **Server-side Firebase Admin env vars added to Vercel production.** `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` were only present in local `quiver/.env` (gitignored), so Vercel-deployed serverless functions had them undefined and `getFirebaseAdminMessaging()` returned `null` on every invocation. That silently no-op'd `POST /api/admin/test-push`, `sendPushNotification()` in `lib/services/push-notifications.ts`, and the FCM branch of `sendPushNotifications()` in `lib/alerts/push-sender.ts` used by `condition-alert-deliver`. This merge exists purely to trigger a Vercel production redeploy so already-warm serverless instances are recycled and pick up the newly-added env vars. No code changes.

### Removed
- **Stopped writing to the dead `user_email_prefs` table from every call site** (plan `abstract-exploring-phoenix` cleanup). E2 confirmed the table is written but never read — no cron, no lib, no hook, no component, no RPC reads any column — but we were routing three writes there anyway: (1) `actions/onboarding-actions.ts` upserted skill_level + email_frequency + min_good_score + timezone + home_beach_id on every completed onboarding (earlier E2 comment claiming the `forecast-digest-email` cron read `user_email_prefs.email_frequency`/`home_beach_id` was wrong on re-audit — that cron reads `profiles.notif_email_enabled` / `notif_forecast_alerts` / `home_beach_id` directly); (2) `app/prefs/home-beach/actions.ts:saveHomeBeach` wrote `user_email_prefs.home_beach_id` when users tapped the old welcome-email "Set your home break" link, so those clicks set a field nobody consumed — a literal no-op from the user's perspective despite appearing to succeed; (3) `app/api/prefs/set/route.ts` wrote `pref_time_bucket` / `skill_level` / `email_frequency` from the old welcome-email preference buttons, same dead pattern. Changes: (1) onboarding upsert removed entirely; (2) `saveHomeBeach` redirected to write `profiles.home_beach_id` (the column Oracle + every downstream read path actually consumes) so users clicking old email links now get what they expected; (3) `/api/prefs/set` converted to a graceful no-op that verifies the token for correct error messaging on tampered/expired links and renders a "link retired" success page for valid tokens — zero DB writes, so users who click 6-month-old welcome emails don't get a 404 or a silently-lying success. Test updates: `__tests__/app/prefs/home-beach/actions.test.ts` now asserts `profiles.update({ home_beach_id }).eq('id', userId)` instead of the old `user_email_prefs.upsert`; `__tests__/app/api/prefs/set/route.test.ts` rewritten to pin the no-op + expired-token-page contract (9 tests → 4). Table itself NOT dropped — per `CLAUDE.md` policy "DROP TABLE for core tables" is prohibited; the drop + type regen is a separate reviewer-gated migration. 101/101 unit tests pass across onboarding + prefs routes; 11/11 e2e regression green (Phase 1A/1B CTA-reduction + onboarding-entry-points). Plan: `abstract-exploring-phoenix` (cleanup).

### Added
- **Server-side `user_events` emission on web intel post + session log writes.** The `/app-stats` dashboard showed `intel_events: 0` and `session_log_events: 0` for the 7d ending 2026-04-17 despite `intel_posts` + `sessions` rows being created — the client-side `track()` in `conditions-report-card.tsx` and `useSessionSubmission.ts` fires GA4 only and never persists to `user_events`. Server actions now emit the corresponding events atomically with the DB write: `actions/conditions-report-actions.ts` fires `intel_post_created` (after intel_posts insert) and `session_log_submit` (after the shadow sessions insert), `actions/session-actions.ts` `createLoggedSession` fires `session_log_submit` after the sessions insert. Both use fire-and-forget IIFEs so user_events failures never fail the user-visible request. Also renamed the GA4 event on the beach-detail Report Conditions submit from `conditions_report_submitted` → `intel_post_created` so GA4 and user_events share one name. Bypasses the `/api/events` UA/bot filter and the Safari ITP / ad-blocker event-drop floor that explains most of the post-signup "invisible cohort" pattern. Observability added to `/api/events/link`: every call emits a structured `events_link_attempt` log with `duration_ms` + `events_updated` so we can measure the signup→link handoff race before deciding whether to make it synchronous in `/auth/callback`. Plan: `yes-grep-the-web-compiled-spark`.

- **Seed a default alert rule on onboarding completion + backfill for 30-day-active existing users.** The condition-alert cron was a silent no-op for every signup because `alert_rules` was empty — no rule, no queue entry, no notification, no retention hook. New `lib/alerts/seed-default-rule.ts` helper inserts one experience-adaptive rule on the user's home beach at the end of `saveOnboardingData`: `beginner`/`intermediate` → `mellow_session` (1-4ft, <8kt, beach's preferred tide window), `advanced`/`expert` → `clean_groundswell` (12s+ period, <10kt, beach's swell window). `experience_level IS NULL` → skipped with telemetry (`metadata.reason: 'no_experience_level'`) — we don't guess. Channel flags (`notify_email`, `notify_push`) mirror the profile's `notif_*_enabled` toggles the user just set, not fabricated defaults. Non-blocking: seed errors are caught, logged as a server `onboarding_step` user_events row with `metadata.step: 'alert_rule_seeded'`, and onboarding still returns `success: true`. Idempotent: bails with `reason: 'already_has_rules'` if the user has any existing rule. Companion migration `20260417134921_backfill_default_alert_rules.sql` seeds the same cohort for existing users where `auth.users.last_sign_in_at > now() - interval '30 days'`, `home_beach_id IS NOT NULL`, `experience_level IS NOT NULL`, and the user has zero existing rules. The backfill uses simpler broad conditions (no per-beach tide/swell-window refinement) to avoid duplicating preset logic in SQL — a wider window is acceptable for the one-time catch-up cohort. 11 helper tests + 5 onboarding-integration tests cover the experience-level matrix, idempotent skip, beach-not-found, channel-flag passthrough, insert errors, and non-blocking behavior. Plan: `what-should-i-use-woolly-raccoon`.

### Fixed
- **Onboarding `?onboarding=required` redirect silently closed the dialog** — Commit B's server-routed redirect for new signups never actually showed the dialog in practice. Initial diagnosis (from an Explore-agent report) was wrong; real root cause found via headless-Playwright instrumentation + module-level store subscription with stack traces. The effect called `reset() + openDialog()`; `reset()` nulls `userId`; React 18 strict-mode dev re-runs the dialog's `checkUserId` effect on the second pass, which sees `state.userId (null) !== user.id` and force-resets the store (setting `isOpen: false`) before the dialog paints. Fix: new `reopenFresh(currentUserId?)` action in `store/onboarding-store.ts` clears `currentStep` + `data` + `isCompleted` + opens the dialog BUT preserves `userId` so the subsequent `checkUserId` pass stays a no-op. Dialog's `?onboarding=required` effect now calls `reopenFresh(user.id)` instead of `reset() + openDialog()`. Two regression tests in `__tests__/store/onboarding-store.test.ts` under a new `describe('reopenFresh')` block pin the invariant — the primary one asserts that after `reopenFresh`, a subsequent `checkUserId(sameUserId)` stays a no-op and does NOT flip `isOpen: false`. Also added `scripts/send-test-welcome.ts` as a reusable Resend-backed welcome-email preview utility (originally written to debug this issue, kept for future email-template testing). Plan: `abstract-exploring-phoenix` (E1).
