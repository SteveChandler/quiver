VERDICT: NOT SAFE — similarity alerts misidentify the configured beach, Bluesky auto-post still selects raw beaches, and the claimed worker/session integration tests do not exercise the real resolver.

## Can the brand be defeated?

Yes. The symbol is private, but the branded type alias is exported (`lib/recommendations/selection/index.ts:15-16`). Any TypeScript caller can explicitly assert a raw value to `RankedBeach<T>`; `any` can also bypass the type checker. The only runtime constructor is itself an unchecked cast (`lib/recommendations/selection/index.ts:72-74`). The brand is intentionally compile-time-only and is lost across JSON serialization (`lib/recommendations/selection/index.ts:3-6`). Therefore it is an invariant for cooperative TypeScript callers, not a security or runtime boundary.

The existing brand test proves only that a plainly typed raw object is rejected (`__tests__/lib/recommendations/selection.test.ts:66-83`). It does not prove resistance to an explicit assertion, `any`, or a JSON round trip. I found no current production `as RankedBeach` call outside the primitive, but that absence does not make the exported alias load-bearing-safe.

## Selection outside the primitive

### Definite policy failures

- **P1 LEAK — Bluesky auto-post.** The edge function fetches San Diego beaches directly (`supabase/functions/bluesky-auto-post/index.ts:759-767`), builds raw scored beaches, applies only `filterScoredBeachesForMajorEventHold`, then sorts and selects from the raw/policy-filtered array (`supabase/functions/bluesky-auto-post/index.ts:1091-1125`). The weekend path likewise sorts and selects `[0]`, names the top beaches, and uses their IDs for the OG image (`supabase/functions/bluesky-auto-post/index.ts:1180-1233`). Longboard Sunday does the same (`supabase/functions/bluesky-auto-post/index.ts:1259-1303`). None of these selections calls `rankBeaches()` or the water-quality resolver; the edge hold policy shown here is the separate major-event authorization path (`supabase/functions/bluesky-auto-post/hold-policy.ts:195-258`). A held beach can therefore be posted, featured, or embedded in an OG recommendation image.

- **P1 LEAK — similarity alert selects/exempts the profile home instead of the configured alert beach.** The rule query omits `alert_rules.beach_id` (`app/api/cron/similarity-alerts/route.ts:451-455`), then stores `profiles.home_beach_id` as the only beach associated with the anchor rule (`app/api/cron/similarity-alerts/route.ts:552-597`). Candidate construction unconditionally keeps that home beach outside `rankBeaches()` while applying the primitive only to alternatives (`app/api/cron/similarity-alerts/route.ts:703-731`). The emitted payload labels the selected slot’s `beach_id` but writes `configured_beach_id: user.home_beach_id` (`app/api/cron/similarity-alerts/route.ts:1052-1060`). The notification adapter turns that one payload field into the exemption set (`lib/recommendations/major-event-hold/adapters/notification.ts:115-126`), and the service exempts by candidate beach ID (`lib/recommendations/major-event-hold/service.ts:98-134`). If the configured rule beach differs from the profile home, a held home beach can be preserved/exempted even though it was not configured, while the user’s actual configured beach is omitted or filtered.

- **P1 OVER-HIDING — similarity alert’s configured beach is not preserved.** The same missing `alert_rules.beach_id` means the route cannot construct the user’s configured beach as the exemption target (`app/api/cron/similarity-alerts/route.ts:451-455`, `app/api/cron/similarity-alerts/route.ts:590-597`). It only builds home/favorite/nearby candidates (`app/api/cron/similarity-alerts/route.ts:603-650`) and filters non-home candidates through the primitive (`app/api/cron/similarity-alerts/route.ts:709-726`). A held beach the user configured for the alert can consequently be dropped or never considered, violating the explicit per-beach alert exemption.

- **P1 LEAK — NPC activity.** NPC beach selection is a raw weighted/random choice from configured or fallback beach rows (`lib/npc/beach-selection.ts:11-30`, `lib/npc/npc-selection.ts:155-219`). The cron then creates content naming and attaching that selected beach (`app/api/cron/npc-activity/route.ts:132-162`, `app/api/cron/npc-activity/route.ts:216-256`). This is Quiver-generated beach selection outside `rankBeaches()`. If the ADR’s “wherever Quiver picks or ranks” rule includes generated NPC community content—which its catch-all wording does—held beaches leak there.

### Other raw selectors found

- The similarity picker itself filters eligibility, sorts, and returns `eligible[0]` without a branded input (`lib/alerts/similarity-best-pick.ts:80-115`). Its caller currently depends on the defective home-beach bypass described above (`app/api/cron/similarity-alerts/route.ts:703-731`).
- Week Scout computes a raw best window with `reduce()` before a later full-pool `rankBeaches()` pass removes held windows (`lib/services/discovery/week-scout.ts:743-789`). The current returned response is sanitized afterward, so I found an escape-prone intermediate selector, not a demonstrated final leak.
- Surf discovery sorts the full raw recommendation pool before applying `rankBeaches()` and then truncates from the safe pool (`lib/services/discovery/surf-discovery-orchestrator.ts:2136-2189`). This is safe at the inspected final boundary, but the pre-filter `allRecs` is not branded.
- The canonical decision engine sorts and selects `[0]` from its input (`lib/recommendations/canonical-decision/engine.ts:206-239`). Its current service caller first passes discovery output through `rankBeaches()` (`lib/recommendations/canonical-decision/service.ts:42-70`), so the inspected web path is safe only because of that upstream boundary.
- The popular-beaches RPC returns an ordered raw pool, but the handler applies `rankBeaches()` before slicing/caching (`app/api/beaches/popular/route.ts:33-48`). The coach-picks RPC is likewise followed by `rankBeaches()` before the result is returned (`app/api/coach-picks/route.ts:106-136`). - The nearby RPC is followed by `rankBeaches()` before final recommendations (`app/api/v1/recommendations/route.ts:190-215`, `app/api/v1/recommendations/route.ts:402-412`; `lib/services/nearby-beach-service.ts:109-117`, `lib/services/nearby-beach-service.ts:179-192`). - The user-match RPC contains an SQL `ORDER BY score DESC LIMIT p_limit` selector (`supabase/migrations/20260715051000_local_match_candidates.sql:161-176`). Repository search found only migration definitions, not an application caller in this worktree; whether an installed native client still calls it could not be determined.

### User-chosen surfaces that intentionally remain outside the primitive

- Search returns all fuzzy matches and its single-name helper returns the best match without water-quality filtering (`lib/utils/beach-search-utils.ts:32-105`). Search-plus-forecast then fetches the selected beach’s forecast (`lib/utils/beach-search-utils.ts:216-255`). This matches the ADR’s visible search/forecast policy.
- Sitemap generation consumes beach rows and builds URLs without a hold filter (`app/sitemap.ts:436-505`), matching the visible sitemap policy.
- User-configured best-days loads enabled `alert_rules.beach_id` and sorts digest slots only for those configured beaches (`lib/alerts/best-days.ts:54-77`, `lib/alerts/best-days.ts:147-158`), which is the intended visible alert exemption.
- Condition-alert evaluation passes the same rule beach as both `beach_id` and `configured_beach_id` (`app/api/cron/condition-alert-evaluate/route.ts:327-342`). ## Pre-migration behavior

The migration is explicitly marked unapplied (`supabase/migrations/20260813140000_create_water_quality_held_beaches.sql:1-5`). When `water_quality_held_beaches` is missing and the query returns `42P01`, the resolver treats that specific condition as resolved with no owner holds and continues to `beach_water_quality` (`lib/recommendations/major-event-hold/water-quality.ts:127-150`, `lib/recommendations/major-event-hold/water-quality.ts:180-250`). This preserves recommendation availability before rollout, subject to the existing quality-table query succeeding.

A real error against an existing hold table returns `unresolved`, as do invalid shapes and unexpected failures (`lib/recommendations/major-event-hold/water-quality.ts:139-150`, `lib/recommendations/major-event-hold/water-quality.ts:152-178`, `lib/recommendations/major-event-hold/water-quality.ts:251-256`). The selection primitive maps unresolved state to an empty ranked list or `null` (`lib/recommendations/selection/index.ts:64-69`, `lib/recommendations/selection/index.ts:76-100`). That is the ADR-required fail-closed behavior inside ranking/discovery (`docs/adr/002-water-quality-holds.md:49-54`).

1. **P1 LEAK — Bluesky edge function bypasses water-quality selection.** Raw beach scoring and `[0]`/top-N selection still feed public posts and OG image URLs (`supabase/functions/bluesky-auto-post/index.ts:759-767`, `supabase/functions/bluesky-auto-post/index.ts:1091-1154`, `supabase/functions/bluesky-auto-post/index.ts:1191-1238`, `supabase/functions/bluesky-auto-post/index.ts:1268-1303`).
