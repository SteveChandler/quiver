## New findings

### P0 LEAK — owner-directed hold table is unapplied and missing-table handling fails open

If the owner-hold migration has not been applied, `resolveWaterQualityHolds` treats SQLSTATE `42P01` for `water_quality_held_beaches` as a **resolved empty hold set** (`lib/recommendations/major-event-hold/water-quality.ts:322-332`). The ranking primitive accepts a resolved empty set and returns candidates, while only an `unresolved` result fails closed (`lib/recommendations/major-event-hold/water-quality.ts:147-155`, `lib/recommendations/selection/index.ts:42-52`, `lib/recommendations/selection/index.ts:79-90`). The seed migration is explicitly marked `UNAPPLIED` and contains five chronic held IDs (`supabase/migrations/20260813140000_create_water_quality_held_beaches.sql:1-20`). This is a direct policy LEAK for every ranking surface if the table is absent.

### P1 LEAK — re-enabled morning post can name held secondary beaches

The route generates the complete regional title/description before it validates the representative beach (`app/api/cron/morning-forecast-bot/route.ts:101-105`). `fetchRegionalForecast` builds a raw beach set capped at 12 (`lib/npc/forecast-formatter.ts:261-280`), selects up to three secondary beaches (`lib/npc/forecast-formatter.ts:328-340`), and `generateRegionalForecast` emits each secondary name into the post (`lib/npc/forecast-formatter.ts:412-416`). Only the representative ID is sent through `selectBeach` (`app/api/cron/morning-forecast-bot/route.ts:124-137`). A held secondary can therefore be named in a Quiver-initiated system post even when the representative is safe.

### P1 LEAK — public beach-list fallback feeds the map without the hold primitive

`GET /api/beaches` returns the full public beach list ordered by name and never calls `rankBeaches` (`app/api/beaches/route.ts:38-45`, `app/api/beaches/route.ts:67-88`). When the nearby API fails, the map fetches that list, computes distance, sorts it, and truncates to 20 directly (`components/map/map-beach-loader.ts:242-265`). This is a Quiver-selected nearby/map surface, so a held beach can appear in the degraded map path. The normal nearby path does rank before slicing (`lib/services/nearby-beach-service.ts:183-207`), but that does not protect this fallback.

### P1 LEAK — coordinate surf endpoint names a raw legacy/static nearest beach

The coordinate branch of `resolveBeach` scans the legacy static dictionary and returns the nearest static name without consulting `selectBeach` (`app/api/surf/utils.ts:135-154`). `getSurfForecast` uses that result as the response beach name and coordinates (`app/api/surf/utils.ts:413-427`), and the public route exposes the result for coordinate requests (`app/api/surf/route.ts:42-48`, `app/api/surf/route.ts:80-83`). The database forecast cache is separately ranked (`app/api/surf/utils.ts:62-73`), so the response can name a held static beach while the forecast was fetched for a different safe database row.

### P1 OUTAGE — County ingest has no atomic claim, so concurrent cron invocations can defeat poll/backoff/circuit state

Each ingest reads state, checks circuit/backoff/poll gates, and only then writes `last_request_at` (`lib/services/county-beach-advisories/ingest-service.ts:99-129`). The repository implements that as an ordinary `select` followed by an `upsert`, with no compare-and-set, lock, or transaction claim (`lib/services/county-beach-advisories/repository.ts:80-95`). Two overlapping invocations can therefore both pass the gate and each fetch the manifest plus all three event types (`lib/services/county-beach-advisories/ingest-service.ts:131-160`, `lib/services/county-beach-advisories/ingest-service.ts:184-189`, `lib/services/county-beach-advisories/types.ts:20-22`). Failure updates also increment the caller’s stale in-memory count (`lib/services/county-beach-advisories/ingest-service.ts:53-77`), so concurrent failures can repeatedly write `consecutive_failures = 1` instead of opening the circuit. The intended backoff and version checks are correct on a serialized run (`lib/services/county-beach-advisories/ingest-service.ts:47-50`, `lib/services/county-beach-advisories/ingest-service.ts:142-160`), but they do not close this race.

### P1 OUTAGE — County schema is also explicitly unapplied

The County tables required by the repository are in an explicitly `UNAPPLIED` migration (`supabase/migrations/20260813170000_create_county_beach_advisory_ingest.sql:1-5`). The only production fetcher construction is in the cron route, which requires cron authentication and invokes the repository ingest (`app/api/cron/county-beach-advisories/route.ts:19-35`, `app/api/cron/county-beach-advisories/route.ts:63-67`); the scheduled entry is every 30 minutes (`vercel.json:119-122`). If the migration is absent, the route’s state read fails and the route returns an error (`lib/services/county-beach-advisories/repository.ts:80-87`, `app/api/cron/county-beach-advisories/route.ts:50-59`). The hold resolver fails closed on the resulting County run-query error, so this is an ingest/outage defect rather than a County fail-open leak (`lib/recommendations/major-event-hold/water-quality.ts:179-196`).

### P2 OVER-HIDING — prefetch capacity is tied to a five-row seed, not runtime hold cardinality

The runtime source of truth is the editable `water_quality_held_beaches` table, while the TypeScript array is only a seed manifest (`lib/recommendations/major-event-hold/water-quality.ts:16-27`, `docs/adr/002-water-quality-holds.md:73-76`). Nevertheless, multiple ranking consumers add only `WATER_QUALITY_HOLD_PREFETCH_BUFFER`, which is fixed at the seed array length of five (`app/[intent]/page.tsx:93-100`, `app/api/beaches/popular/route.ts:34-48`, `lib/services/nearby-beach-service.ts:110-120`). If the owner adds more than five holds, raw ordered/top-N sources can return fewer safe results than requested after the correctly ordered filter. This is OVER-HIDING, not a leak.

### P2 TRUST — future CEDEN rows are rejected too late to be harmless to the source window

The internal station read is genuinely paginated: it orders by stable ID and walks 1,000-row ranges until a short page (`lib/services/water-quality/water-quality-sync-service.ts:169-198`), and both station consumers use it (`lib/services/water-quality/water-quality-sync-service.ts:850-856`, `lib/services/water-quality/water-quality-sync-service.ts:1009-1015`). The sample window is anchored to UTC today and evaluation is bounded through UTC today (`lib/services/water-quality/water-quality-sync-service.ts:885-895`, `lib/services/water-quality/water-quality-sync-service.ts:1046-1052`, `lib/services/water-quality/water-quality-sync-service.ts:1084-1092`). However, the CEDEN SQL orders all rows descending and applies a single 32,000-row limit (`lib/services/water-quality/water-quality-sync-service.ts:43-47`, `lib/services/water-quality/water-quality-sync-service.ts:661-669`); future rows are rejected only after that response is received (`lib/services/water-quality/water-quality-sync-service.ts:687-694`). A future row cannot be upserted or directly affect evaluation, but it can consume the source limit and push a valid in-window row out of the fetched set. That can indirectly produce incomplete water-quality evidence.

### P2 OUTAGE / OVER-HIDING — a post-completion state-write failure rewrites a completed County run as failed

The ingest marks the run completed before saving the success state (`lib/services/county-beach-advisories/ingest-service.ts:192-210`). If that state write throws, control enters the catch block, calls `failRun`, and marks the same run failed (`lib/services/county-beach-advisories/ingest-service.ts:226-233`, `lib/services/county-beach-advisories/repository.ts:153-158`). The resolver selects only the latest completed run (`lib/recommendations/major-event-hold/water-quality.ts:169-197`), so this failure can discard the freshest usable County snapshot and leave ranking unresolved until a later successful run.

## Verified correct

- County outbound access is confined to the cron construction path found in this tree: the route comments that it is the only constructor, instantiates the fetcher, and passes it into ingest (`app/api/cron/county-beach-advisories/route.ts:19-35`). Request-time hold resolution reads completed snapshots from the application database rather than constructing the County client (`lib/recommendations/major-event-hold/water-quality.ts:164-183`).
- The two-hour boundary is strict: the configured limit is two hours (`lib/services/county-beach-advisories/types.ts:24-29`) and `fetched_at` is stale when `now - fetchedAtMs >= COUNTY_MAX_STALENESS_MS` (`lib/recommendations/major-event-hold/water-quality.ts:212-223`). At 2h01m the County sub-resolution is `unresolved`; with the owner-hold table query available, the composite ranking result is therefore unresolved and ranking fails closed (`lib/recommendations/major-event-hold/water-quality.ts:448-463`, `lib/recommendations/selection/index.ts:83-90`). The canonical beach page remains a direct user-chosen surface and continues fetching its page data (`app/[intent]/[city]/[beachSlug]/page.tsx:118-170`).
- Unmatched County sites are retained with `beach_id = null`, counted as unique unmatched sites, and included in the run summary (`lib/services/county-beach-advisories/normalizer.ts:66-100`). The ingest warns the operator with the matched/total/unmatched counts (`lib/services/county-beach-advisories/ingest-service.ts:212-216`), and the migration permits the nullable foreign key (`supabase/migrations/20260813170000_create_county_beach_advisory_ingest.sql:40-58`). They are not silently dropped.
- The County client handles request timeout/HTTP failures as transient, checks both version-change flags, and rejects changed exception/shape payloads (`lib/services/county-beach-advisories/county-client.ts:110-135`, `lib/services/county-beach-advisories/county-client.ts:187-216`).
- The main reviewed recommendation boundaries do pass through the primitive before consuming a top result: featured beaches filter the source before building the landing list (`lib/data/server/featured-beaches.ts:444-477`), discovery ranks the full scored pool before its hold/truncation stages (`lib/services/discovery/surf-discovery-orchestrator.ts:2170-2201`), and system-card selection retries rejected candidates through `selectBeach` (`lib/npc/system-card-selection.ts:50-83`, `lib/npc/system-card-selection.ts:143-147`).
