# Phase 20.1: Durable Beach Follow And Surf-Call Retention Loop - Context

**Gathered:** 2026-08-24
**Status:** Ready for planning and execution
**Repositories:** `quiver`, `quiver-native`
**Insertion:** Urgent decimal phase after completed Phase 20 and before Phase 21

<domain>
## Phase Boundary

Phase 20.1 turns Quiver's broad web beach traffic and small native user base into one measurable repeat-use loop without assuming every web visitor is a surfer.

The web product owns the durable object: **a beach the visitor cares about**. It must continue serving water-temperature, tide, weather, safety, travel, swimming, fishing, paddling, and general beach intent without forcing a surf identity or hiding the answer behind sign-in.

The native product owns the surf-specific temporary object: **the recommendation Quiver made for a beach and window**. It must preserve the question and recommendation context, notify only when the answer is useful or materially changes, and capture a lightweight outcome after the window.

The phase implements this loop:

```text
Web beach utility
  -> Follow this beach
  -> qualify intent only when evidence exists
  -> exact beach/window handoff for surf-qualified visitors
  -> native Home continuity
  -> Watch this call
  -> still-on/material-change update
  -> one-tap outcome
  -> visible learning receipt
  -> better next recommendation
```

This phase does **not** add a Planning -> Decision -> Execution state machine. Native continues to use the existing `Now`, `Best`, and `My spots` product model. It also does not create a generic beach native app.

</domain>

<decisions>
## Implementation Decisions

### Product Roles

- **D-01:** Web is a broad coastal utility and audience-qualification surface. Native remains a dedicated surfing product.
- **D-02:** A water-temperature, tide, weather, or beach page view alone never classifies a visitor as a surfer.
- **D-03:** The durable cross-surface object is the beach. A surf call/window is temporary context attached to that beach.
- **D-04:** Web success and native product health remain separate scorecards. Generic web traffic is not evidence of native retention or subscription value.

### Web Beach Ownership

- **D-05:** The universal web ownership action is `Follow this beach`, not `Download the app` and not `Watch this surf call` for every visitor.
- **D-06:** The first follow works without an account using durable first-party local state. Sign-in is requested only when sync, email, notifications, or cross-device access creates clear value.
- **D-07:** A follow stores selected topics such as water temperature, tide, beach conditions, water quality, or surf conditions. The exact enum and storage shape are planner discretion, but surf must not be the default for unknown intent.
- **D-08:** A signed-in merge must preserve anonymous follows, avoid duplicate beaches/topics, and never silently delete account follows.
- **D-09:** `My Coast` is the first owned web destination. It adapts to the visitor's followed beaches and topics. Surf rankings and exact calls appear only when the visitor is explicitly or defensibly surf-qualified.
- **D-10:** High-traffic utility pages answer the original query before presenting follow, comparison, signup, notification, or app-handoff actions. Existing canonical URLs, structured data, and page intent remain unchanged.

### Intent Qualification

- **D-11:** Intent has three evidence states: `explicit`, `inferred`, and `unknown`. Explicit user choice outranks inference.
- **D-12:** Supported explicit intents may include surfing, swimming, beach days, fishing, diving/paddling, and other. Planning may simplify labels but cannot collapse everyone into surfing.
- **D-13:** Surf inference requires multiple surf-specific signals or one high-intent action such as comparing surf spots, opening detailed swell/wind/tide context, saving a surf alert, or using an exact surf-window handoff. A single utility view is insufficient.
- **D-14:** Intent evidence is used for relevance and measurement, not sensitive profiling. Analytics stores safe enums and counts, not raw search text, notes, coordinates, or PII.

### Exact Web-To-Native Handoff

- **D-15:** Surf-qualified calls to action preserve the exact beach, window, recommendation identity, source page, and anonymous attribution token through universal link, App Store fallback, and joined native first open.
- **D-16:** The native app opens the exact resolvable beach/window context that caused the handoff. It does not drop the user into generic onboarding or require the same search again before showing value.
- **D-17:** Extend the existing `/app/spot/:slug?window=:id` routing, AppDeepLinkCTA, attribution, and first-open join contracts. Do not create a second link router or incompatible attribution system.

### Native Continuity And Watching

- **D-18:** Native preserves or explicitly expires the selected Home mode. A silent `Best` -> `Now` remount is not acceptable.
- **D-19:** Week Scout stability must be enabled for all production users through `EXPO_PUBLIC_WEEK_SCOUT_STABILITY_ENABLED=true`, shipped in the production client bundle, device-verified, and observable. The emergency rollback remains available.
- **D-20:** `Best` retains its accepted recommendation through small forecast revisions and replaces it only under the existing material-change/invalid-incumbent contract. `Now` remains live and is not made sticky.
- **D-21:** Recommendation changes identify the actual cause: forecast shift, mode transition, location change, candidate-set change, filter change, or startup context refinement. Do not label every replacement as forecast intelligence.
- **D-22:** `Watch this call` is the primary one-tap surf ownership action on eligible Home and Beach Detail calls. It reuses existing alert/watch infrastructure and captures known context automatically. Advanced tuning remains optional.
- **D-23:** Notifications are decision-relevant only: still on, materially changed, clearly better nearby, or post-window feedback. Generic engagement pushes and daily-open prompts are out of scope.
- **D-24:** Notification taps open the exact watched context with enough prior/current state to understand why Quiver interrupted the user.

### Outcome And Learning

- **D-25:** After a watched window, the default feedback is a one-tap 1-5 outcome with beach, time, recommendation, forecast, and board context prefilled.
- **D-26:** The existing full session log remains available but is not required to close the watched-call feedback loop.
- **D-27:** After feedback, Quiver shows a truthful learning receipt describing what was saved or updated. It must not claim model learning that did not actually occur.
- **D-28:** Reuse existing session, recommendation attribution, feedback, offline/pending, and personalization primitives. Do not create a second session-history system.

### Measurement And Rollout

- **D-29:** Measurement separates general coastal visitors, surf-qualified web visitors, signed-in/existing Quiver users on web, and native users.
- **D-30:** Before/after and holdout evidence is required. Raw event counts alone cannot prove that following, watching, or feedback caused retention.
- **D-31:** Rollout begins on selected high-traffic beach and beach-water-temperature templates, not a site-wide mass template change.
- **D-32:** Expansion requires page-intent, Core Web Vitals, canonical/schema, notification quality, attribution, and native device gates to pass.

### Scope Fences

- **D-33:** No worldwide rollout, localization, new ML model, broad social feed, generic streak system, full Apple Watch parity, or Android-first expansion in this phase.
- **D-34:** Do not retarget water-temperature pages as surf reports or make surf the dominant CTA for unknown-intent visitors.
- **D-35:** Do not add a new alert composer, favorite model, recommendation engine, session log, deep-link router, or analytics transport where an existing primitive can be extended.
- **D-36:** Database migrations, production deploys, outbound email/push sends, entitlement changes, and all-user mobile releases retain their existing approval gates.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- Web already has intent-aware templates, beach/water-temperature pages, app CTAs, exact-window links, anonymous analytics, and an alert-capture CTA.
- Native already has favorite/home beaches, condition alerts, Alert Center, exact-window routing, recommendation attribution, Week Scout stability logic, session logging, offline handling, and post-recommendation feedback primitives.
- Phase 20 already established the app-link route and before/after measurement contract. Phase 20.1 extends that work instead of replacing it.

### Established Patterns

- Keep server data in existing query/service patterns; do not add a new client state framework for follows or watched calls.
- Use existing Supabase auth/RLS and approval-gated migrations if account sync needs additive persistence.
- Keep anonymous web state first-party, versioned, bounded, and mergeable.
- Use existing event-taxonomy and anonymous-event allowlists. New metadata is safe enums, IDs, booleans, bands, and counts only.
- Preserve canonical URL, page-intent, structured-data, and source-honesty rules from Phases 14-20.
- Native UI remains dark-only and follows current typography, haptics, accessibility, and TanStack Query conventions.

### Integration Points

- Follow actions should attach to high-traffic beach and water-temperature surfaces without displacing the answer.
- My Coast should reuse existing beach cards, condition summaries, canonical links, and saved/favorite data where possible.
- Surf-qualified CTAs should extend `AppDeepLinkCTA` and the existing first-open attribution join.
- `Watch this call` should seed the existing alert/watch contract from Home or Beach Detail, not require a user-built condition rule first.
- Post-window feedback should attach to the watched recommendation identity and reuse existing session/recommendation attribution storage.

</code_context>

<specifics>
## Specific Ideas

- Utility CTA: `Follow this beach`.
- Surf CTA after qualification: `Open this exact call in Quiver`.
- Native CTA: `Watch this call`.
- Native update examples: `Still on`, `Call changed`, `Better nearby`, `How was it?`.
- My Coast should answer `What changed at the beaches I care about?`, not merely list bookmarks.
- Best alternatives must retain their own time/window and be labeled `Other opportunities` unless they are true same-window runner-ups.

</specifics>

<deferred>
## Deferred Ideas

- Generic beach-native modes for swimming, fishing, tourism, or paddling.
- Full lifecycle email nurture beyond the follow/update contract proved in this phase.
- Broad user-generated public condition reporting, social feeds, and heatmaps.
- Worldwide catalog expansion, Spanish/Japanese localization, and international launch campaigns.
- Full watch/wearable session tracking.
- New recommendation ML or formal model-training infrastructure.

</deferred>
