# Plan 20.1-05 Task 3 — Week Scout stability flag: configuration truth and prepared change

**Investigated:** 2026-08-25, by the Phase 20.1 execution session (controller).
**Method:** read-only inspection of every configuration source that can supply an
`EXPO_PUBLIC_*` value to a build or an OTA update. No configuration was changed.
**Base:** `quiver-native` merged main `92c41245`.

## Finding: the flag is not set anywhere. Stability is OFF for every user, in every channel.

`src/lib/week-scout/stability-flag.ts` is the single reader:

```ts
export function isWeekScoutStabilityEnabled(): boolean {
  return process.env.EXPO_PUBLIC_WEEK_SCOUT_STABILITY_ENABLED === 'true';
}
```

An exhaustive search for `WEEK_SCOUT_STABILITY` across configuration returns **no matches** in:

| Source | Supplies build/OTA env? | Contains the flag? |
|---|---|---|
| `eas.json` → `development` profile | yes | **no** (no `EXPO_PUBLIC_*` keys at all) |
| `eas.json` → `preview` profile | yes | **no** (8 other `EXPO_PUBLIC_*` keys) |
| `eas.json` → `production` profile (channel `production`) | yes | **no** (same 8 keys) |
| `eas.json` → `firebase-production` profile (channel `production`) | yes | **no** |
| `app.config.js` (incl. `extra:`) | yes | **no** |
| `quiver-native/.env*` in the primary checkout | yes — `scripts/release-ota-production.sh` sources `.env.production` | **no** |
| `scripts/`, `.github/` | build/publish time | **no** |

The only two references in the repository are the reader above and its own unit test, which sets
the variable in-process.

**Consequence:** `process.env.EXPO_PUBLIC_WEEK_SCOUT_STABILITY_ENABLED` inlines as `undefined` in
every bundle, so `isWeekScoutStabilityEnabled()` returns `false` in the shipped 1.0.2 / build 17
binary and in every published OTA on the `production` channel — including "build 16 #7"
(groups `855044e6` iOS / `a3fabe98` Android, source `68fa66fb`).

This supersedes the softer N-01A wording ("bundled value rides the build profile; device truth
open"): no device check is required to establish the current value, because no configuration
source can produce `'true'`. A device diagnostic is still worth capturing under N-01B to confirm
the *runtime* reading matches this static conclusion.

## Impact on BFR-08

BFR-08 requires Week Scout stability to be "shipped enabled for all production users through the
approved mobile build/configuration". That requirement is **not met today**, and the shortfall is
not a rollout-percentage question — the feature has never been enabled for anyone. Plan 20.1-05
Task 2 wires Home's `Best` through the stability resolver, but that path stays inert in
production until this flag is set.

## Prepared change (NOT applied — requires Steven's approval)

Enabling for all users is a one-line addition to the approved production configuration, plus a
republish. Recommended placement is the `production` **and** `firebase-production` EAS profiles
(so binaries carry it) *and* `quiver-native/.env.production` (so OTA updates carry it), because
the two paths supply env independently:

```jsonc
// eas.json → build.production.env  AND  build.firebase-production.env
"EXPO_PUBLIC_WEEK_SCOUT_STABILITY_ENABLED": "true"
```

```sh
# quiver-native/.env.production  (uncommitted, operator-held)
EXPO_PUBLIC_WEEK_SCOUT_STABILITY_ENABLED=true
```

**Rollback:** remove the value (or set anything other than the literal `true`) and republish the
OTA; the reader's strict `=== 'true'` comparison means any other value disables it. Because the
value is build-time-inlined, a rollback requires a new OTA/build — there is no runtime kill
switch for this flag today. If a runtime kill switch is wanted, that is a separate change and
should be decided before broad rollout, not after.

**Approval gates that remain:** setting production configuration, publishing an OTA or binary,
and any claim of all-user rollout. None were performed. Per the phase rules this document is the
prepared change plus evidence, not a rollout.

## What to verify once approval lands (order matters)

3. Confirm PostHog receives `baseline_created`, `incumbent_retained`, and `recommendation_replaced`

4. Only then may BFR-08 be described as shipped; until step 3 produces events, it stays
