# Phase 20.1: Durable Beach Follow And Surf-Call Retention Loop - Research

**Researched:** 2026-08-24
**Status:** Complete enough for execution planning
**Evidence sources:** PostHog project 424662, current `quiver` and `quiver-native` source, issues #155/#76, prior Phase 20 app-link and measurement artifacts

## Executive Finding

Quiver does not have one stickiness problem. It has two different products with two different jobs:

- The **web** receives broad, mostly anonymous coastal utility traffic. Many visitors may be swimmers, travelers, anglers, paddlers, parents, or beachgoers rather than surfers.
- The **native app** has a much smaller user base whose strongest repeated behavior is manually opening Home, Explore, and Beach Detail to check current or near-term surf conditions.

The AllTrails pattern is useful only when translated correctly:

- AllTrails' durable object is a trail. Quiver's durable object is a beach.
- AllTrails' temporary layer is weather/conditions. Quiver's temporary layer is a surf recommendation/window.
- AllTrails converts research into ownership through Save and Lists before it depends on payment. Quiver should convert utility traffic through Follow this beach before it depends on app download or subscription.
- AllTrails makes native essential during the outing. Quiver must make native essential by preserving the call, monitoring meaningful changes, using the surfer's boards/preferences, and learning from the result.

The highest-leverage phase is therefore not more SEO inventory or a larger feature set. It is a durable beach-follow relationship on web connected to a low-friction watched-call loop in native.

- The phase should make Home continuity and watching reliable before adding more destinations.

## Competitive Pattern: What AllTrails Actually Solves

AllTrails works because it creates a complete object lifecycle:

```text
Find a trail
  -> save it
  -> organize it
  -> open the exact trail in native
  -> use native during the outing
  -> record/complete/review
  -> improve personal history and public trail information
```

The important product mechanics are:

1. The public page is useful before account creation.
2. Save is the first ownership action; subscribe is not.
3. The durable object syncs exactly between web and native.
4. Native performs a job the web cannot perform as well.
5. The post-activity action improves the user's record and future product value.
6. Paid value is confidence, safety, convenience, and advanced planning—not merely more raw data.

Quiver's translated lifecycle is:

```text
Find a beach utility page
  -> follow the beach
  -> qualify surf intent only when evidence exists
  -> open the exact beach/window in native
  -> preserve and watch the surf call
  -> notify on still-on or material change
  -> rate the outcome in one tap
  -> improve the next recommendation
```

## Recommended Data Contracts

These are planning constraints, not final schema prescriptions.

### Beach Follow

A durable follow needs:

```text
follow_id or deterministic beach identity
beach_id or canonical beach reference
anonymous_id and/or user_id
selected_topics[]
created_at
updated_at
source_surface
version
```

Rules:

- Anonymous local follow must function without a database write.
- Account sync may use existing favorites if the semantic contract fits. Do not create parallel `favorites` and `follows` that silently disagree.
- Topic selection must preserve general coastal intent.
- Merge is idempotent and union-based unless the user explicitly removes a topic or beach.

### Intent Evidence

```text
intent = surfing | swimming | beach_day | fishing | diving_paddling | other
source = explicit | inferred
confidence = optional bounded enum/band
signals_count = bounded number
updated_at
```

Rules:

- `unknown` is represented when no defensible evidence exists.
- Explicit choice overrides inference.
- Water temperature alone does not add a surf signal.
- Do not persist raw search queries or sensitive free text.

### Exact Surf Handoff

```text
handoff_token
beach_id / slug
window_id or stable window identity
window_start / window_end
recommendation/decision identity when available
source_page_type
source_path_class, not raw sensitive URL params
anonymous_id
created_at / expires_at
```

Rules:

- Token is bounded and expires.
- App Store fallback preserves the token for first-open join.
- Native resolves server truth rather than trusting a stale client payload as the current recommendation.
- The previous web context remains available for explanation and attribution.

### Watched Call

Prefer extending existing alert/watch storage with:

```text
beach_id
window identity
mode = now | best
recommendation identity
created forecast/scorer version
board context when available
watch state
last evaluated state
notification history
```

Rules:

- One tap creates a useful watch from known context.
- Advanced condition editing is optional.
- Small Best revisions retain the incumbent; material/invalid changes replace it.
- `Now` stays live.

### Outcome

```text
watched_call_id / recommendation identity
rating = 1..5
actual surfed = yes | no | skipped/unknown, if needed
board_id when already known
submitted_at
full_session_id optional
```

Rules:

- Rating alone is sufficient.
- Full session logging is optional and can enrich the record later.
- Offline/pending behavior reuses existing outbox semantics.
- Learning receipt reflects actual persisted effects only.

## Risks And Mitigations

| Risk | Mitigation |
|---|---|
| Web becomes a generic lifestyle product with no Quiver conversion | Keep native surf-specific; measure surf-qualified funnel separately |
| Water-temperature pages lose intent or SEO performance | Answer first, limited template pilot, canonical/schema/CWV regression gates |
| Follow duplicates existing favorites | Mandatory repository/data audit and one semantic ownership contract |
| Signup wall suppresses the first ownership action | Anonymous local follow before account request |
| Exact handoff still drops context after App Store | Expiring handoff token plus first-open join and physical-device verification |
| Watch becomes another complex alert builder | One-tap default; advanced tuning secondary |
| Push spam increases opt-outs | Decision-relevant event types, caps, dedupe, quiet hours, and holdout measurement |
| Recommendation changes erode trust | Preserve Home mode, all-user stability, and explicit change reasons |
| Feedback creates a second session system | Attach lightweight outcome to existing recommendation/session primitives |
| Learning receipt overclaims | Receipt generated from actual persisted update/result |
| Small samples produce false confidence | Minimum sample rules, confidence intervals where practical, and holdouts |

## Planner Questions To Resolve

1. Can existing signed-in favorite/home beach records support topic-bearing follows, or is one additive table required?
2. Which anonymous local-storage version and merge policy best fits existing auth hydration?
3. Which exact high-traffic templates form the first pilot cohort?
4. Which existing alert rule type can represent a watched call without exposing advanced configuration?
5. How is a watched call reevaluated server-side, and what existing cron/worker can own it?
6. Which session/recommendation table is the correct home for a lightweight outcome?
7. Which exact native builds/channels currently contain the Week Scout stability flag, and how will all-user activation be proven?
8. Which PostHog dashboards and holdouts can separate novelty from sustained retention?

## Recommended Phase Order

The phase should run before worldwide expansion and before major forecast-map investment because it tests whether existing traffic and recommendation capability can produce repeat use.

It is inserted after Phase 20 because it depends on the completed universal-link, exact-window, and analytics foundations. Phase 21 remains important but is sequenced afterward while this urgent activation/retention gap is addressed.
