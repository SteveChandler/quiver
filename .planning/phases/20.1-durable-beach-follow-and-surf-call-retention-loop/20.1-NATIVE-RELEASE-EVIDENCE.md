# Phase 20.1 Native Release Evidence Without An Owner Device

**Added:** 2026-08-24  
**Owner constraint:** Steven does not currently have a physical iPhone available for validation.  
**Effect:** Native implementation continues. Physical-device-only claims are delegated and remain release gates.

## Decision

The former `N-01` gate is split into two independent gates:

### N-01A — Build and release metadata truth

**Owner:** implementation/release worker  
**Physical phone required:** no  
**Blocks code work:** no  
**Blocks release preparation:** yes, until metadata is captured  
**Blocks all-user completion claim:** no by itself; N-01B still required

Capture from source control, App Store Connect/TestFlight metadata, Expo/EAS build and update records, CI/build logs, and compiled configuration evidence:

```text
app version
build number
build profile
target environment
runtime version
EAS channel
update ID, when an OTA exists
source commit and source branch
native binary fingerprint/dependency state
EXPO_PUBLIC_WEEK_SCOUT_STABILITY_ENABLED value used by the target build
rollback build/update/config path
captured-at timestamp
```

The value must be proven from the target build/update inputs or a safe runtime diagnostic. Repository defaults alone are insufficient.

N-01A may be completed with no physical device. It should be completed before publishing or asking a tester to validate a build, so the tester is testing a known artifact.

### N-01B — Delegated physical-device behavior proof

**Owner:** Steven coordinates; one trusted external TestFlight/iPhone tester executes  
**Physical phone required:** yes, but it does not need to belong to Steven  
**Blocks code work:** no  
**Blocks simulator/internal implementation evidence:** no  
**Blocks production/all-user rollout and BFR-08 completion:** yes

A trusted external iPhone user may satisfy this gate. Prefer an existing Quiver TestFlight user who can provide a screen recording and diagnostic screenshots.

Minimum validation script:

1. Install or update to the exact build identified in N-01A.
2. Capture app version, build number, runtime/channel/update identity, and the Week Scout stability diagnostic.
3. Open Home and select `Best next 24h`.
4. Capture the accepted beach/window and timestamp.
5. Terminate and relaunch the app; verify the selected mode and valid call restore or explicitly expire.
6. Verify a sub-margin refresh retains the incumbent while details update, using an approved deterministic fixture or test condition when live conditions cannot produce the case safely.
7. Verify a material/invalid-incumbent replacement shows previous call, current call, and actual cause.
8. Create `Watch this call` and verify idempotent watched state.
9. Receive/open one approved real push on the physical device and verify exact-context routing. Simulated payload routing is supplementary, not a replacement for production APNs proof.
10. Confirm PostHog receives the expected normal-user stability/watch/open events for that tester without PII.

Required artifacts:

```text
tester pseudonymous ID
phone model and iOS version
TestFlight/App Store environment
build/runtime/channel/update/source identity
screen recording or screenshots
PostHog event references
pass/fail by validation step
observed defects
captured-at timestamp
```

## Delegation options

Use one of these, in order:

1. Existing trusted Quiver TestFlight user.
2. Team member, founder, friend, or contractor with an iPhone added to TestFlight.
3. A managed real-device testing provider only when it supports the required installed-build, APNs, relaunch, and diagnostic workflow; provider limitations must be documented.

A simulator remains valid for deterministic UI, state, deep-link, and injected-notification routing tests. It cannot close production APNs delivery, installed TestFlight artifact identity, or real-device relaunch evidence.

## Release disposition when N-01B is unavailable

The team may:

- finish contracts and implementation;
- run unit, component, integration, simulator, and build-time configuration verification;
- prepare an internal/TestFlight build after normal approval;
- mark BFR-08 and physical notification/exact-link criteria `Blocked — external physical-device validation required` with owner and next action.

The team may not:

- claim Week Scout stability is live for all production users;
- mark BFR-08 complete;
- claim production push delivery/tap routing is proven;
- promote the feature to all users solely from simulator or source-default evidence.

## Recommended diagnostic support

Plan 20.1-05 should expose a safe support/diagnostic view or structured diagnostic event containing only:

```text
app version
build number
runtime version
channel
update ID
source commit
stability flag boolean
release environment
```

No secrets, access tokens, user email, raw coordinates, or private forecast evidence may be exposed. This diagnostic reduces dependence on developer-owned hardware and makes external validation reproducible.

## Workflow replacement

Where existing Phase 20.1 documents say `N-01` or require Steven to capture physical-device truth personally, interpret them as:

- **N-01A:** capture artifact/configuration truth without a phone;
- **N-01B:** delegate physical behavior validation before all-user release completion.

N-01B is a release gate, not an implementation gate.
