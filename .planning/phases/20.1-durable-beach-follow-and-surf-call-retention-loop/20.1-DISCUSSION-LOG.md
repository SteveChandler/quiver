# Phase 20.1: Durable Beach Follow And Surf-Call Retention Loop - Discussion Log

**Date:** 2026-08-24
**Status:** Product direction captured

## Conversation Sequence

### 1. Three-Month Product Review

The initial review combined web growth with native product health. Steven corrected that framing: web should not be used to make the native release appear healthier. Web users and native users need separate behavior and retention analysis.

Decision:

- Web is measured as acquisition/utility unless the visitor is signed in or otherwise joined to the product identity.
- Native is measured as the surf product.

### 2. What Users Actually Do

The review found:

- Web is dominated by one-off search utility, especially beach and water-temperature information.
- Native's repeated behavior centers on Home, Explore, and Beach Detail.
- Alerts and sessions have too little adoption to claim that either currently drives the business.

Decision:

- Do not force web and native into one undifferentiated DAU/retention metric.
- Build repeat-use loops around the surfaces people already use.

### 3. Recommendation Continuity Correction

A proposed Planning -> Decision -> Execution model did not match the code. The native app actually uses `Now`, `Best`, and `My spots`; there is no persisted planned-session commitment in this flow.

Code review found:

- Home remounts with `Now` selected.
- `Now` and `Best` answer different questions.
- foreground/hourly refreshes rerank recommendation queries;
- cold start can issue a location-only discovery request and then a second request after saved/excluded context settles;
- Best alternatives may come from different windows and are not necessarily same-window runner-ups;
- Week Scout stability exists behind a build-time flag.

Decision:

- Preserve the existing modes.
- Persist or explicitly expire the selected mode.
- Explain why a recommendation changed.
- Enable Week Scout stability for all production users.
- Track this native continuity work in `quiver-native#155` and the stability rollout in `quiver-native#76`.

### 4. Stickiness Strategy

The first stickiness strategy assumed many web visitors were prospective surfers. Steven corrected that assumption: most may not be surfers.

Decision:

- Web serves broad coastal intent.
- Native remains surf-specific.
- A water-temperature page view alone never qualifies surf intent.
- Conversion should be measured against surf-qualified visitors, not all web visitors.

### 5. AllTrails Analogy

The discussion examined how AllTrails handles broad, episodic outdoor intent:

- public pages provide useful answers before account or payment;
- the durable trail can be saved and organized;
- exact trail context syncs to native;
- native performs an outing-specific job;
- post-outing recording/review improves personal and public value;
- premium value is confidence, safety, convenience, and advanced planning.

Quiver translation:

- Trail -> beach.
- Save trail -> Follow this beach.
- Lists -> My Coast.
- Hit the Trail -> Open this exact call in Quiver.
- On-route update -> still-on/material-change surf update.
- Record/review -> one-tap outcome plus optional full session log.

Decision:

- The beach is durable; the surf call is temporary.
- Web should establish beach ownership before requiring native install or subscription.
- Native must remember what it told the surfer and make outcomes improve future value.

### 6. GSD Phase Request

Steven requested a GSD phase for the strategy.

Decision:

- Add urgent decimal Phase 20.1 to the active `quiver` Go-Live Campaign milestone.
- Place it after completed Phase 20 app-link/analytics foundations and before Phase 21.
- Treat it as cross-repository work across `quiver` and `quiver-native`.
- Make it executable in small waves with explicit measurement and approval gates.

## Locked Product Language

Preferred universal web action:

> Follow this beach

Preferred qualified web-to-native action:

> Open this exact call in Quiver

Preferred native action:

> Watch this call

Preferred update categories:

- Still on.
- Call changed.
- Better nearby.
- How was it?

Labels to avoid without supporting data:

- Calling every web visitor a surfer.
- Calling cross-window alternatives runner-ups.
- Presenting a mode reset or location change as a forecast shift.
- Claiming Quiver learned when no persisted personalization update occurred.

## Non-Goals Reaffirmed

- No generic beach native app.
- No Planning / Decision / Execution state machine.
- No new ML model.
- No duplicate alert composer, favorite store, link router, or session log.
- No worldwide expansion or localization in this phase.
- No generic daily streak or engagement push strategy.
