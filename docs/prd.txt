Project: Quiver—Community-Driven Surf Sessions Tracker & PredictorAuthor: Product TeamDate: May 7, 2025Version: 2.0

1. Document Purpose and Scope

This PRD outlines the vision, objectives, functional and non-functional requirements, and high-level design for Quiver, a mobile-first surf app that enables surfers to plan, log, review, and predict surf sessions. It targets community engagement and integrates real-time forecasting.

Scope Includes:

Community features (reviews, media sharing)

Session planning & logging

Quiver management (personal boards)

Real-time surf forecasts

Enhanced social features and community building

Real-time condition reporting

Advanced gamification and progress tracking

Scope Excludes:

In-app purchases (Phase 3)

Offline-first sync beyond basic caching

Advanced AI-driven wave analysis (v3)

2. Vision & Goals

Vision: A community‑driven, trail‑style surf app where surfers can plan sessions, share experiences, leverage accurate forecasts, and build meaningful connections within the surf community.

Goals:

Empower surfers with reliable surf forecasts and real-time conditions

Build an engaged community sharing reviews, media, and experiences

Provide personal logging for skill progression and equipment tracking

Foster social connections and crew-building among surfers

Create localized surf communities with regional customization

3. Target Audience & Personas

Beginner Ben: New to surfing; seeks guidance on when/where to surf safely, wants to connect with other beginners

Regular Riley: Experienced surfer; tracks sessions, compares conditions, shares media, builds surf crew

Traveler Taylor: Visits new beaches; relies on community reviews, forecasts, and local knowledge

Community Curator Chris: Active contributor who shares conditions, reviews, and helps others in the community

4. User Journeys

Plan a Session:

Open Home, tap "Plan Session," select nearest beach or search, view forecast, choose time & board, save.

Log a Session:

After surf, tap "Log Session," pick beach, board, rate conditions, add notes & photos, submit.

Browse Beaches:

From Map/List, filter by region, tap beach for detailed forecast, veteran reviews & gallery.

Manage Quiver:

In Profile, add a new board (type, dimensions, photo), edit or remove existing boards.

Engage Community:

Rate a beach, comment on others' sessions, like media posts.

5. Functional Requirements

5.1 User Profiles (Phase 1 - Implemented)

Sign up / log in via Supabase Auth (email/password, social).

Profile details: avatar, display name, bio.

View own session history, boards, contributions.

5.2 Beach Directory (Phase 1 - Implemented)

Map & list views showing clickable beach markers.

Integrate third‑party surf API for forecasts (e.g. Surfline).

Display beach information and locations.

5.3 Session Logging (Phase 1 - Implemented)

Form: beach, board, date/time picker, wave height, water temperature, crowd density, parking ease, notes.

Store session data in Supabase PostgreSQL.

5.4 Quiver (Personal Boards) (Phase 1 - Implemented)

Add/edit/delete board entries: name, dimensions, type, photo.

Select board when planning/logging sessions.

5.5 Media Uploads (Phase 2 - Priority)

Upload photos & videos with metadata tags (beach, session).

Thumbnail generation & streaming via Firebase Storage.

Session photo galleries with tagging capabilities.

Image optimization and compression.

5.6 Community Reviews & Interaction (Phase 2 - Priority)

Rate factors (1–5 stars) and freeform comments.

Beach review system with categories.

Like/comment functionality on reviews and sessions.

Follow users and activity feeds.

6. Non‑Functional Requirements

6.1 Performance & Scalability

API response < 200ms for core endpoints.

CDN for media assets.

Auto‑scale Supabase & Firebase.

6.2 Security & Privacy

Enforce HTTPS everywhere.

Role‑based access: authenticated vs. public.

Data encryption at rest & in transit.

GDPR & CCPA compliance for user data.

6.3 Reliability & Availability

99.9% uptime target.

Automated health checks & alerts.

6.4 Maintainability

Modular codebase: components/, lib/, types/.

CI/CD: GitHub Actions for Next.js builds & Supabase migrations.

6.5 Localization

Support English at launch; architecture for additional languages.

7. Technical Architecture

7.1 Tech Stack

Frontend: Next.js (App Router), Tailwind CSS, Shadcn UI

Backend: Supabase (PostgreSQL, Auth, API)

Media Storage: Firebase Storage & CDN

├── app/                # Next.js pages & layouts

users (id, name, email, avatar_url, bio)

beaches (id, name, coords, description)

sessions (id, user_id, beach_id, board_id, timestamp, ratings JSON, notes)

boards (id, user_id, name, dimensions, type, photo_url)

reviews (id, user_id, beach_id, rating, comment, timestamp)

media (id, user_id, session_id or beach_id, url, type, timestamp)

12.1.3 Established Patterns (USE THESE) ✅

✅ Data Fetching Pattern:
```typescript
const fetchData = useCallback(async () => {
  return await someAction();
}, [dependencies]);
const { data, loading, error, refetch } = useDataFetcher(fetchData);
```

✅ API Route Pattern:
```typescript
import { createSuccessResponse, handleApiError } from '@/lib/api-utils';
export async function POST(request: Request) {
  try {
    const result = await processRequest();
    return createSuccessResponse(result);
  } catch (error) {
    return handleApiError(error);
  }
}
```

✅ Server Action Pattern:
```typescript
import { withAuthenticatedAction } from '@/lib/server-action-utils';
export const myAction = withAuthenticatedAction(async (userId, ...args) => {
  // Action implementation
});
```

12.3 Architecture Compliance Standards

✅ Required for ALL New Features:
1. Database Schema: Proper RLS policies and indexes
2. Server Actions: Use authentication wrappers from lib/server-action-utils.ts
3. API Routes: Use centralized error handling from lib/api-utils.ts
4. Data Fetching: Always use useDataFetcher with proper memoization
5. Components: Follow established patterns and component structure
6. Real-time Features: Use Supabase subscriptions properly
7. Testing: Unit tests for utilities, integration tests for features

❌ Patterns to AVOID:
- Manual loading state management (use useDataFetcher)
- Inline async functions in hooks (causes infinite loops)
- Direct database access without authentication
- Custom error handling (use centralized utilities)
- Unmemoized fetch functions (use useCallback)
