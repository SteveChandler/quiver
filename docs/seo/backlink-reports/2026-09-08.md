## New finding 1: `/{state}/{unknown-city}` is a soft 404

`/{valid-state}/{unknown-city}` returns **HTTP 200** with the title
**"Location Not Found | Quiver"** and **two conflicting robots directives**.
Reproduced 5/5 on `/ca/los-angeles`.

| URL | HTTP | robots meta | Title |
| --- | ---: | --- | --- |
| `/ca/los-angeles` | **200** | `index, follow` **and** `noindex` | Location Not Found |
| `/fl/miami` | **200** | `index, follow` **and** `noindex` | Location Not Found |
| `/ny/new-york` | **200** | `index, follow` **and** `noindex` | Location Not Found |
| `/or/portland` | **200** | `index, follow` **and** `noindex` | Location Not Found |
| `/ca/zzzz-not-a-city` | **200** | `index, follow` **and** `noindex` | Location Not Found |
| `/xx/nowhere` | 404 | `noindex` + `noindex, follow` | Page Not Found |
| `/ca/san-diego/zzzz-not-a-beach` | 404 | `noindex` + `noindex, follow` | Page Not Found |
| `/water-temp/zzzz-nope`, `/tide/zzzz-nope`, `/cams/zzzz-nope`, `/surf-cams/zzzz-nope` | 404 | `noindex` + `noindex, follow` | Page Not Found |

**Scope is narrow and worth saying precisely.** Only the `/{state}/{city}` route
does this. Every other unknown route returns a correct 404. The page body is the
site chrome with no content — the visible text is navigation and footer only.

**Severity is moderate, not high.** Google resolves conflicting robots meta to the
most restrictive value, so the `noindex` should win and indexing risk is low. The
real cost is a **200-response surface unbounded by any real city list**, one valid
state code times any slug, at a moment when the Ahrefs crawl reports **5,544
uncrawled URLs**. A scan of every `/{st}/{city}` link on 7 hub pages and
`/beaches/usa` found **no internal links into this surface**, so nothing on the site
is actively feeding it; the exposure is external links, typed URLs, and crawler
guessing. The contradictory `index, follow` tag should not be emitted regardless.

`/hi/waimea` was the one city in the 186-page scan with no robots tag: it is a
**301 to `/hi/waimea-kauai`**, which is correct behaviour.

family is indexed, so the two families are inconsistent with each other. That is the
decision to make, and this run did not make it.

### Manual export pipeline — root-caused and repaired this run

Five consecutive reports raised `[DROP EXPORT]` for a backlink CSV. All five named
`Brand-Vault/seo-audit/<audit-date>/`. **That folder is the wrong target.**
`discoverManualBacklinkExportFiles` searches **two** directories
(`lib/seo/agent-workflow/backlink-proxy.ts:44`):

```
[ Brand-Vault/seo-audit/<audit-date>/ ,  quiver/docs/seo/backlink-reports/ ]
```

The dated folder resets every Monday, so a file dropped there is invisible to the
next run. The stable folder is not. An export **was** supplied on 2026-08-25 —
`Brand-Vault/seo-audit/2026-08-25/REFERRING-DOMAINS.csv`, 214 rows — it was read once,
and every report since has asked for it again while the file sat on disk unreachable.

Repaired this run, uncommitted:

| Change | File |
| --- | --- |
| Export persisted to the stable folder, filename carrying its capture date | `docs/seo/backlink-reports/REFERRING-DOMAINS-2026-08-25.csv` |
| `capturedAt` added to `ManualBacklinkExport` | `lib/seo/agent-workflow/types.ts` |
| Capture date read from filename, file mtime as fallback; stem matcher tolerates a trailing `-YYYY-MM-DD` | `lib/seo/agent-workflow/backlink-proxy.ts` |
| New `Backlink manual export` row in the source-freshness table | `scripts/seo/weekly-report.ts` |
| Capture date surfaced in the Backlink / Referrer Signals narrative | `lib/seo/agent-workflow/weekly-report.ts` |

Persistence alone would have traded "missing input" for "silently stale input", which
